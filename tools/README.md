# tools/build_docs.py

Generates the per-app privacy, terms and support pages published on
**www.nexomalabs.com**, and rewrites `sitemap.xml`.

The Markdown files are the single source of truth. The script renders each one
into a styled HTML page that matches the main site, so the same document is
available both as raw Markdown and as a page a person (or an App Store reviewer)
can actually read.

- **Requirements:** Python 3.9 or newer. Standard library only — nothing to install.
- **Run it from the repository root**, not from inside `tools/`.

---

## Commands

```bash
python3 tools/build_docs.py           # regenerate everything
python3 tools/build_docs.py --check   # verify without writing; exit 1 if stale
python3 tools/build_docs.py --help    # flag reference
```

Both commands are idempotent and safe to re-run. `--check` writes nothing.

---

## Everyday task: edit a document

```bash
vim hundy/PRIVACY.md                 # 1. edit the Markdown — this is the source
vim hundy/app.json                   # 2. bump "updated_date"
python3 tools/build_docs.py          # 3. regenerate
git add hundy/ sitemap.xml           # 4. commit BOTH the .md and the .html
git commit -m "Update Hundy privacy policy"
```

> **Never hand-edit a file carrying the generated marker.** The next build
> overwrites it. Edit the Markdown instead. (A page you wrote yourself, with no
> marker, is safe — see "Hand-authored pages" below.)

> **Always commit the generated HTML.** There is no CI build step — GitHub Pages
> serves exactly what is in the repository, so uncommitted output means a stale
> page is live. `--check` exists to catch this.

## Everyday task: add a new app

```bash
mkdir newapp
cp hundy/app.json newapp/          # then edit every field
$EDITOR newapp/PRIVACY.md          # write these yourself — see below
$EDITOR newapp/TERMS.md
python3 tools/build_docs.py
```

**Write the documents yourself.** Do not copy another app's privacy policy and
change the name: a privacy policy is a factual claim about what that specific
app does with data, and an inherited one is usually wrong. `hundy/` is worth
reading as an example of the shape and tone, not as text to reuse.

`hundy/` also shows the optional pattern: a hand-written `index.html` landing
page plus an `FAQ.md`, instead of the generated index and a `SUPPORT.md`.

No list to update anywhere. The script discovers **any** directory at the
repository root that contains an `app.json`, except the reserved names
`assets/`, `tools/`, and anything beginning with a dot.

The directory name becomes the URL segment, so `mkdir newapp` produces
`https://www.nexomalabs.com/newapp/privacy`. Use lowercase and hyphens —
`habit-tracker`, not `Habit Tracker`.

## What each app directory must contain

```text
hundy/
├─ app.json        SOURCE     metadata (see below)
├─ PRIVACY.md      SOURCE     required; also served raw
├─ TERMS.md        SOURCE     required; also served raw
├─ SUPPORT.md      SOURCE     optional; also served raw
├─ FAQ.md          SOURCE     optional; also served raw
├─ privacy.html    GENERATED
├─ terms.html      GENERATED
├─ support.html    GENERATED  only if SUPPORT.md exists
├─ faq.html        GENERATED  only if FAQ.md exists
├─ index.html      GENERATED  unless you wrote your own — see below
└─ assets/         YOURS      anything else in the folder is left alone
```

`PRIVACY.md` and `TERMS.md` are required; a missing one aborts the build.
`SUPPORT.md` and `FAQ.md` are optional — each is rendered only if present, and
an app that lacks one simply has no such page and no sitemap entry for it.

### Hand-authored pages are never overwritten

Every generated file carries this marker on its second line:

```html
<!-- generated by tools/build_docs.py - do not edit -->
```

If a file the generator would write **already exists without that marker**, it
is treated as hand-authored and left completely alone. The build reports it:

```
kept  hundy/index.html (hand-authored, not overwritten)
```

This is how an app can have a real landing page at `/hundy/` instead of the
generated document index. Write your own `index.html`, and the generator will
step around it forever. The same protection covers any generated filename.

To hand a page back to the generator, delete it and rebuild.

### Your own titles and dates win

- The page heading comes from the document's own `# H1` when it has one, falling
  back to the generic label in `DOC_TYPES`. A document titled `# Terms of use`
  renders as "Terms of use", and sibling pages link to it by that name.
- If the document states its own date — any `Last updated` or `Effective date`
  text near the top — the template omits its own date line rather than printing
  a second, conflicting one. Apps whose documents carry no date get the line
  from `app.json`.

### app.json

Every key is required and must be non-empty.

| Key | Appears | Example |
| --- | --- | --- |
| `name` | Page headings, `<title>`, body text | `"Gym Body - Fitly"` |
| `category` | Eyebrow label on the app index | `"Mobile Product"` |
| `tagline` | Lead paragraph on the app index | `"A fitness companion..."` |
| `support_email` | Contact panel on every page | `"support@nexomalabs.com"` |
| `effective_date` | Date line under the page title | `"August 27, 2026"` |
| `updated_date` | Date line under the page title | `"August 27, 2026"` |

Dates are free text and are printed verbatim — they are not parsed, so keep the
format consistent by hand. They are **not** read from the Markdown; the
`**Effective date:**` line inside a `.md` file is separate prose that you should
keep in sync manually.

## URLs this produces

For an app directory named `hundy`:

| URL | Served file |
| --- | --- |
| `https://www.nexomalabs.com/hundy/privacy` | `privacy.html` |
| `https://www.nexomalabs.com/hundy/terms` | `terms.html` |
| `https://www.nexomalabs.com/hundy/support` | `support.html`, if `SUPPORT.md` exists |
| `https://www.nexomalabs.com/hundy/faq` | `faq.html`, if `FAQ.md` exists |
| `https://www.nexomalabs.com/hundy/` | `index.html`, generated or your own |
| `https://www.nexomalabs.com/hundy/PRIVACY.md` | `PRIVACY.md` (raw) |

**Submit the extensionless HTML URLs to App Store Connect** —
`/hundy/privacy` for the privacy policy, and for the support URL either
`/hundy/support` or, for an app that ships a landing page instead, `/hundy/`. GitHub
Pages serves a raw `.md` file as `text/markdown`, which browsers show as
unformatted source or download outright; that is not a page a reviewer should be
sent to. The `.md` URLs exist for linking from the app repositories.

`/hundy/privacy` and `/hundy/privacy.html` both work. Use the `www.` host — the
apex domain issues a 301 redirect to it.

Relative asset paths are written so a page renders correctly whether it is
reached with or without the `.html` extension.

## Supported Markdown

The renderer implements the subset these documents actually use:

| Feature | Syntax |
| --- | --- |
| Headings | `#` through `####` |
| Bold / italic | `**bold**`, `*italic*` |
| Inline code | `` `code` `` |
| Links | `[text](https://example.com)` |
| Autolinks | `<https://example.com>` |
| Italic (underscore) | `_italic_` |
| Email | bare `name@example.com`, auto-linked to `mailto:` |
| Lists | `-` or `*`, and `1.` |
| Tables | GitHub pipe tables, header row plus `|---|` separator |
| Blockquote | `> quoted` |
| Rule | `---` |

Notes:

- A leading `# H1` is consumed and replaced by the page template's own title, so
  it never renders twice. Keep it — it is what makes the raw `.md` readable.
- **Raw HTML in Markdown is escaped, not passed through.** This is deliberate,
  so a stray `<` in legal text cannot break a page. `<script>` becomes visible
  text, never an executable tag.
- External links get `target="_blank" rel="noreferrer"`; internal links to
  `www.nexomalabs.com` and relative links do not.

### Unsupported syntax — avoid these

Anything outside the table above is not handled, and some of it fails *quietly
and wrongly* rather than being left alone. Verified behaviour:

| You write | You get | |
| --- | --- | --- |
| `- a`<br>`  - nested` | Both items flattened to one level | **silent data loss** |
| `![alt](photo.png)` | `!` followed by a text link | mangled |
| ` ```code fence``` ` | Backticks and `<code>` tags interleaved | mangled |
| `[label][ref]` | Literal `[label][ref]` | harmless |
| `Text[^1]` | Literal `[^1]` | harmless |

The first three are the dangerous ones. If a document needs a nested list,
restructure it as a `###` subheading with a flat list underneath.

## Troubleshooting

| Message | Meaning |
| --- | --- |
| `error: hundy/TERMS.md is required but missing.` | `PRIVACY.md` or `TERMS.md` is absent. The optional ones never error. |
| `kept hundy/index.html (hand-authored...)` | Not an error. A file without the generated marker was left untouched. |
| `error: hundy/app.json is not valid JSON: ...` | Syntax error in the manifest — usually a trailing comma or a single quote. |
| `error: hundy/app.json is missing required key(s): support_email` | Add the key, or give it a non-empty value. |
| `No app directories found (each needs an app.json).` | You ran the script from inside `tools/`. Run it from the repository root. |
| `out of date: hundy/privacy.html` | `--check` found generated output older than its source. Run the build and commit the result. |

Every failure exits non-zero and writes nothing.

## Preview locally

```bash
python3 -m http.server 5500
```

Then open <http://localhost:5500/hundy/privacy.html>.

The local server does **not** resolve extensionless URLs — `/hundy/privacy`
returns 404 locally but works on GitHub Pages. Use the `.html` form when
previewing.

## Extending the script

- **Add a document type** (for example `EULA.md`): append a tuple to
  `DOC_TYPES` and a matching entry to `DOC_BLURBS`. It is optional by
  default; add it to `REQUIRED_DOCS` to make every app carry it.
- **Change the domain:** edit `SITE_URL`. It drives canonical tags, Open Graph
  URLs and the sitemap.
- **Change page styling:** edit the `.doc-*` rules at the bottom of
  `assets/style.css`. The generated markup reuses the main site's CSS variables,
  so it follows the light/dark theme automatically.
- **Change page structure:** the `head()`, `footer()`, `doc_page()` and
  `app_index()` functions hold the HTML templates.

After any change, run `python3 tools/build_docs.py` and commit the regenerated
files.
